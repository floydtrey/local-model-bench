## Runtime/durability prerequisites

The installed Windows Python 3.12.10 links **SQLite 3.49.1**. It is not safe for operational multi-connection WAL under the documented reset race. No environment or live installation was changed. Stage A `connect()` defaults to fail closed unless the actual linked version is 3.51.3+, a 3.50.7-or-later 3.50 backport, or a 3.44.6-or-later 3.44 backport. Offline synthetic schema/backup tests explicitly use `validation_only=True`; this flag is not permission to deploy an affected runtime. GitHub CI prints actual linked Python/SQLite versions and operational gate results on every supported matrix job. Before B operational wiring, reuse a native patched Python/SQLite distribution and verify the exact linked binary/version in the intended installation. Version strings alone cannot attest a vendor binary; release provenance must be checked at cutover.

The [SQLite WAL-reset advisory](https://www.sqlite.org/wal.html#walresetbug) states that multiple connections writing/checkpointing concurrently can corrupt affected WAL databases. One queue controller does not mean one DB connection. No custom scheduler or background checkpointer is introduced. Operational use is gated rather than claiming a nondeterministic timing test proves safety. Tests verify acceptance/rejection of affected/fixed version boundaries and refusal before a file is created. Later connection topology, checkpoint policy and runtime verification are explicit B/C prerequisites, with all connections using the same configured entry point. Raw sqlite3 callers can bypass application policy and must not be used operationally.

Configured connections verify WAL, synchronous FULL, foreign_keys ON, recursive_triggers ON and busy_timeout 5000 ms. Recursive delete triggers plus migration 5 insert-conflict guards prevent replacement writes from rewriting append-only records, including alternate unique-key conflicts. Full durability depends on truthful filesystem/VFS/device flushes and local disk operation. WAL is not a universal power-loss proof and is unsuitable for shared network filesystem use. Do not copy a live `.sqlite3` file alone: committed data may still be in WAL. [SQLite's backup API](https://www.sqlite.org/backup.html) supplies a consistent database snapshot, including committed WAL state; Stage A uses it rather than raw copying.

File data is flushed with fsync after copy and manifests are flushed before promotion into a new destination. Promotion uses same-parent rename to a previously absent directory. This supports visibility/recoverable publication, but does not claim arbitrary Windows directory metadata or rename survives power loss. [Microsoft's MoveFileExW documentation](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) describes WRITE_THROUGH flushing in the copy/delete case; it does not establish general rename durability. Stage B must reconcile absent/pending directories and DB references after restart, retain original snapshots and report unavailable evidence honestly.

## Implemented backup and restore

`backup(connection, artifact_root, new_destination)` resolves paths and rejects source/destination root overlap before creating any directory, then refuses an open transaction or existing destination, uses SQLite backup API into an isolated pending directory, converts the snapshot to DELETE journal mode for portability, checks current schema ledger plus integrity_check/foreign_key_check, and enumerates artifact references from that snapshot. Verified artifacts are copied with streaming SHA-256/size checks and fsync. Missing/unverifiable/corrupt historical references stay recorded in the unavailable list rather than acquiring invented evidence. Manifest identifies format/schema, all copied files/hashes/sizes and unavailable artifact IDs. Full manifest/DB registry/path/file verification runs before promotion. A verified artifact that is absent or tampered aborts without a final destination.

`verify_backup(directory)` rehashes every file, validates schema/integrity/FKs, checks artifact registry against manifest and rejects duplicate/unsafe paths, extra files, missing files and inconsistent declarations. Canonical relative paths prohibit traversal/absolute/Windows drive paths; symlinks and Windows reparse paths are rejected. Trusted artifact-root ACLs and immutable writes are required to prevent concurrent malicious path replacement; these helpers do not claim to implement a sandbox or authenticate an untrusted manifest. Hashes detect changes against a trusted original; an attacker rewriting both data and manifest requires an independently authenticated checksum/signature. No stored scripts are executed.

`restore(backup_directory, new_destination)` resolves paths and rejects overlap in either direction (including aliases and staging beneath the source) before any directory creation, then verifies first, copies and hashes into a new pending root, re-verifies the complete copy, then promotes. Restored structure is `database.sqlite3`, `artifacts/`, `manifest.json`. It never overwrites an existing installation. If promotion is interrupted, the original verified backup remains usable. Regression tests compare the retained source byte hashes and full tree before/after every rejected overlap, verify it remains readable, then perform a safe sibling restore and re-verify both copies. Do not use a restored database operationally until the patched-runtime gate, external artifact root, native ownership and later cutover acceptance are verified. A portable snapshot can be inspected offline; operational connection reapplies durability pragmas.

Deterministic tests exercise WAL snapshot inclusion, exact restored records/artifacts, optional unavailable evidence, corruption/missing files, hostile manifest paths, extra/omitted files, refusal inside a transaction/existing destination, and no promotion on failure. They test transactional/visibility contracts and integrity, not physical power cuts or device firmware behavior. Original installation backups were independently rechecked; their 7,421 source files / 55,795,857 bytes, CRC/hashes, paused 14-item queue and all three Git bundles currently verify. Those private audit records are kept outside public GitHub.

## Durable publishing and restart contract for B

The schema supports (without activating) scheduled → started → execution completed/interrupted → evidence finalized → assessment completed/unavailable → result committed → review pending/completed. Lifecycle records are append-only audit observations; Stage A intentionally has no event dispatcher or live transition service. Existing runner/assessor/controller still own each action. B must implement the state transition validation and exact per-case protocol-derived evidence finalization, hash validation, assessment content binding and transaction boundary, using existing sealed artifacts instead of competing outputs.

The publication transaction links exact attempt, independent assessment and verified snapshot/artifact references. PASS cannot be inserted from exit code alone, interrupted/blocked execution or missing required evidence. Successful evidence constraints are a defensive floor: file-byte validation and human/assessor authenticity belong to the existing publishers and future authorized API boundary. No SQL flag proves semantic qualification. Missing assessments remain unavailable, not inferred. Any failure rolls back that case's pending metadata while completed cases remain committed. Files finalized before DB commit may become orphans; reconcile by exact hashes and lineage rather than auto-publish.

Restart preserves completed cases; incomplete attempts are recorded honestly with no fabricated assessment, no automatic rerun and no advance to a dependent Worker step. Queue snapshot restoration must go through existing native recovery semantics and process-custody checks. Owner must authorize explicit resume or rerun. Review completion never gives execution authority. Technical approval, public visibility, authenticated Owner control and private/public reading remain separate server-side scopes for future stages.
